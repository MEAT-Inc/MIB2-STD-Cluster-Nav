# Android Auto projected navigation focus

The v15 run `_disconnect_observer_20261119_132442_fb46ba95` recorded nine projected focus requests (SAL event 0x1749, app 90, thread 1, native value 1). The hook deferred all nine. The test had an unlimited route deadline, zero projected releases and one discarded pending request on physical disconnect. The last request was at unit monotonic 515110 ms and the verified service stop was at 533550 ms. The focus hook did not reach a 30-second release deadline.

Stock DSI/HMI focus 2 means projected. In AndroidAutoServices, 0x1124e0–0x1124f8 maps DSI focus 2 to native SAL value 1. The serializer at 0x131f14 writes the value and unsolicited flag to event 0x1755. AndroidAuto reads that event and passes its focus to 0x113674, whose native value 1 branch (0x113690–0x1136a8) calls 0x119840 with 1. AndroidAuto’s opposite branch at 0x1136b0–0x1136c0 calls it with 0.

For the observed AndroidAuto executable, 0x119840 forwards that flag to its sink helper at 0x11f620. In the nonzero branch, the relative string at 0x11f7a0 resolves to `NAV_FOCUS_PROJECTED` and the helper passes protocol enum 2 at 0x11f704. The zero branch references `NAV_FOCUS_NATIVE` via 0x11f7a4 and passes protocol enum 1 at 0x11f724. Both reach `Controller::setNavigationFocus` through the call at 0x120dc0. In the captured receiver, the Controller at 0x75528 puts the incoming enum in `NavFocusNotification` at 0x75550 and builds control message 0x0e. The protobuf serializer at 0xbb700 writes that enum as field 1.

v15 called the helper with 0 after holding the HMI listener event. It therefore requested native phone focus while the phone was requesting projected focus. v16 should pass 1 in the eligible hold path. The fixture checks the actual argument presented to the acknowledgement helper, and the packaging gate requires the fixture marker.

The wrong focus value is a concrete defect and can account for a pending radio-start route or a phone-started route that later aborts. The capture records helper calls and video transport, so it cannot establish the phone’s internal timeout or its reason for ending guidance. On-car acceptance should start guidance from the radio and then from the phone, with each route kept active beyond 60 seconds, and record the Guidance UI, audible instructions, cluster display, and terminal route-policy report. Confirm that cancelling a route and physically unplugging the phone continue to restore native focus.
