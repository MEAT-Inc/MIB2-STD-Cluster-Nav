Android Auto discovery investigation: Delphi MST2_US_VW_P0890D
=============================================================
Scope: offline read-only analysis of acquired files in this Source workspace.
No vehicle connection, hook installation, binary patching or acquired-code execution.

Confirmed protocol handshake
----------------------------
libautoreceiver.so Controller::sendVersionRequest is at VA0x74fc0.
It allocates six bytes and constructs 00 01 00 01 00 03:
  0x74fe8 mov r1,#1; 0x74fec strb r1,[r0,#1] (message id 1)
  0x74ff8 strb r1,[r3,#1] after r3=r0+2 (major 1)
  0x75004 mov r2,#3; 0x75008 strb r2,[r3,#1] after r3=r0+4 (minor 3)
  0x75028 queues six bytes through queueOutgoingUnencrypted.
This is Delphi stock protocol 1.3, not the MHI2 hook's stock 1.2. Phone behavior
at any modified version is not proven and advertising a newer minor is not a
substitute for actually implementing that protocol surface.

Endpoint construction/registration
----------------------------------
AndroidAuto application:
  0x12174c operator new(0x50) -> constructor 0x12165c at 0x121774.
  The constructor's vtable relocation resolves to _ZTV9VideoSink at GOT0x176570
  (PC-literal reconstruction at0x121664/0x12169c). This identifies it as the
  actual VideoSink, not merely a similarly sized application wrapper.
  Constructor parameters include this, service ID byte, router pointer and a
  byte stored at+0x30. Full semantic meaning/lifetime of that byte is not proven.
  Constructor initializes callback shared_ptr+0x34, config vector+0x3c, +0x4c.
  0x124ccc is the application wrapper initialization routine.
  0x124d04 allocates an 8-byte callback adapter, constructor0x125ca0.
  0x124d78 sets the sink's IVideoSinkCallbacks shared pointer.
  0x124d98 sets sink+0x1c to4 (setup/ack window parameter, not service ID).
  0x124e50 calls GalReceiver::registerService(this,endpoint).
  0x125010 calls VideoSink::addSupportedConfiguration.
  0x125138 calls VideoSink::setVideoFocus.
The constructor is inline/local; it is NOT an exported VideoSink constructor.
Calling a fixed address or copying its layout remains firmware-specific.

Library:
  GalReceiver::registerService0x76fac delegates to MessageRouter::registerService.
  MessageRouter::registerService0x7f54c reads endpoint service ID at byte+0x0c,
  rejects ID0xff or an occupied slot, and stores endpoint at router+0x100+4*id.
  It does not allocate IDs. A second endpoint needs a confirmed unused ID.
  onChannelOpened0x82834 records channel byte+5 and marks byte+4 ready.
  VideoSink::handleDataAvailable0x8d9e0 dispatches through callback+0x38,
  virtual table slot+0x0c; data offset and media session are part of its ABI.
  MediaSinkBase::ackFrames0x7e650 generates protocol message0x8004 and queues on
  that endpoint's channel. VideoSink::setVideoFocus0x8db50 similarly emits0x8008.
  MediaSinkBase::sendConfig0x7e744 is generic and queries vtable+0x3c for config
  count. Endpoint registration is general enough that a second VideoSink is a
  plausible porting target, but construction/destruction/concurrency are not
  yet runtime validated. No specific spare service ID has been verified.

Discovery serialization: key hook candidate
------------------------------------------
Controller::sendServiceDiscoveryResponse0x756c4:
  0x76198 MessageRouter::populateServiceDiscoveryResponse
  0x761c0 MessageRouter::marshallProto(message_id=6, response, IoBuffer*)
  0x761ec MessageRouter::queueOutgoing(channel, data+offset, end-offset)
  0x761f4 frees the backing buffer.
A wire-level transformation after the stock marshaller is a candidate way to
inject modern display metadata without overwriting C++ object internals.
Buffer capacity, ownership, framing, all error paths and allocator identity
must be recovered before implementing such a runtime hook.

Why MHI2 hook offsets cannot be copied
-------------------------------------
Primary reference reviewed:
https://github.com/chopinwong01/mhi2-android-auto-video-vc/blob/main/src/video_sink_hook.c
Conceptually useful exported interfaces (registerService, addSupportedConfiguration,
addDiscoveryInfo, focus, acknowledgments) match in name/signature. The object ABI
is different. Upstream injects display_id/type via an unknown-field std::string
inside its MediaSinkService, starting at object+8 and length+0x18. Delphi uses
+4 available_type, +8 audio_type and hasbits+0x54, with its serializer emitting
only fields1-5 and no trailing unknown-field append. Its 0x58-byte generated
object is not the upstream layout. Those raw writes would corrupt fields here.
The parent report's missing schema field is therefore a porting requirement,
NOT proof of impossibility. A wire-level extension is independently testable.
Upstream also has a much larger callback-handler class; Delphi's visible 8-byte
adapter allocation must not be replaced using upstream callback sizes/constructors.

Host-only wire fixture and validation
-------------------------------------
scripts/android_discovery_wire_fixture.py uses Python standard library only.
add_cluster_descriptor() preserves the original ServiceDiscoveryResponse bytes
and appends a copied video Service descriptor with a distinct illustrative ID.
It tags only the new media descriptor with field6 display_id=1 and field7
CLUSTER=1. It preserves main descriptor and unrelated extension fields verbatim.
It rejects occupied IDs, ambiguous templates, malformed lengths/varints and
unsupported protobuf groups. Its new descriptor is merely a host fixture:
NO receiver endpoint, input service, focus handling or video transport exists.
All six tests pass, with a separate byte-walking decoder for assertions.
Parent independently reran those tests successfully.

Saved sample main/dual responses and decode summary demonstrate wire encoding
only, not phone acceptance. Fixture IDs2 and64 are illustrative, not recovered
Delphi runtime values. No copyrighted firmware bytes are used in fixtures.

Next minimal gates
------------------
1. Audit MessageRouter::marshallProto and IoBuffer methods to recover exact
   header length/ownership/capacity. Model the transform and allocator contract
   on host buffers, including failure rollback without affecting primary output.
2. Recover complete VideoSink vtable, base constructor, callback virtual ABI,
   shared-pointer refcounts and cleanup paths; build ABI assertions from actual
   bytes before considering a disposable on-car diagnostic hook.
3. Verify pairing requirements for cluster InputSourceService and modern phone
   negotiation using a legitimate DHU reference; this is separate from proving
   old Delphi compatibility. Parent prepared phone-only DHU guidance.
4. Register an actual second endpoint and a real paired input endpoint before
   any runtime discovery advertisement. Merely appending this fixture's bytes
   would create a descriptor whose incoming channel has no receiver.
5. Preserve primary sink behavior; secondary focus and ack lifetimes need their
   own state and backpressure. No test on the vehicle is needed yet.

Limitations
-----------
PLT labels use the observed ARM header20/entry12 layout and ELF relocations.
Some disassembly ranges include literal pools; they are not executed code.
No live service-discovery capture, phone response, or secondary video stream
has been observed on this Delphi unit. No installer or deployable hook exists.
