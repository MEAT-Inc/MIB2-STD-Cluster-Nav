TransportServer follow-up: copy ownership, saturation and writer exclusivity
==========================================================================
Offline static audit only. No vehicle connection, patch or live writer.
Evidence: native-transport-server-disassembly.txt generated by
scripts/native_transport_server.py. Addresses apply only to this P0890D dump.

io_write and buffer ownership
----------------------------
io_write starts0x1053e4. After iofunc_write_verify, it allocates requested
nbytes+4 at0x105634-0x10563c. It synchronously copies the client's data with
resmgr_msgread at0x1054e4, looping until the requested count has been read.
The copy starts four bytes after the allocation; the byte count is stored
at allocation[0] at0x105508. Therefore a successfully completed write does
not leave TransportServer referencing the client's original payload buffer.

Channel::write0x110a4c -> thunk0x11069c -> Queue2::tryPush0x10b578 enqueues
the allocated block pointer. tryPush locks its mutex and compares
queued_payload_bytes+new_block_payload_bytes with maximum_bytes at0x10b604.
Acceptance is strictly less-than; equality is rejected too. On acceptance,
the pointer enters the deque, queued-byte count increments and a reader
condition is signaled. There is no wait-for-space path in this routine.

Saturation/return behavior
-------------------------
tryPush rejection returns internal0x49. io_write frees the allocated copy
at0x105590 and sets ctp+0x48 reply count to0 at0x105594-0x105598; its handler
return remainsEOK. Thus this normal saturation path produces write()==0,
not EAGAIN/ENOSPC, and is all-or-zero per submitted write buffer. Success
sets the reply count to the full copied count at0x1055a0. Allocation failure
returns12; verification errors are returned directly. Unexpected/failed
resmgr_msgread progress is not robustly checked by the observed copy loop.
No claim of finite blocking latency: mutex acquisition and client IPC can
block even though queue saturation itself does not wait for free space.

The native map callback submits separate pointer/length entries and ignores
short/zero writes. A future prototype must detect zero progress and preserve
TS framing; blindly repeating the native callback's error handling can lose
one segment of a TS packet. No live retry/writer implementation was added.

Successful reader lifetime
--------------------------
io_read0x104a00 obtains data via Channel::read0x1109ac ->0x10df9c.
The consumer pops the allocated block using waitPop2 at0x10afd8; empty
queue waits on a condition. The popped length is subtracted from queued
bytes immediately. Partial consumption retains the block pointer+offset in
the reader state. Fully consumed blocks enter a retained list via0x111b7c,
so the returned IOV pointers stay valid after the handler returns. At the
start of the next read, Channel begin-read0x1109a4 ->0x10deec ->0x1119fc
frees that retired list; actual free call is0x111a14. The IO handler returns
negative IOV count at0x104c88, consistent with QNX resource-manager vectored
reply semantics. Queue capacity excludes a block already popped into a
reader's partial state. Reader-close/cancellation and abnormal teardown
lifetimes were not exhaustively audited; do not assume them proven safe.

Single writer
-------------
Writer registration0x1108d4 takes the channel lock, tests writer slot+0x48
against-1, stores the connection id only when empty, otherwise returns0x160
at0x110900. Status decoder0x10d0e4 maps0x160 to "channel : already open for
write". io_open calls this registration at0x105acc and rejects nonzero
status, returning0x59 from0x105bb0. A competing writer cannot simply share
the existing isoTX channel. Writer shutdown0x110854 resets the slot to-1;
its complete coordination with MOST/control connection teardown is not yet
recovered. Open/close strategy must be designed before any vehicle test.

Remaining narrow questions
--------------------------
Actual configured queue maximum; MOST consumer read sizes/lifecycle; complete
reader-close/cancellation cleanup; authoritative SAL clock units; active
cluster dimensions/frame-rate/codec settings. No new acquisition needed now.
