Runtime bridge: first confirmed trace
====================================
Source: latest successful runtime collection, manifest hashes verified.
No car connection, deployed code or live SAL messages.

screen-cda is the missing external-map control bridge:
- SAL_Get_Config at0x11d6a0, config application byte set0x55 at0x11d6a4/6a8,
  config passed to SAL_Init at0x11d880-0x11d888.
- Dispatcher compares event0x1693 at0x11afe4, dispatches to0x11c0c4.
- Handler checks payload length8 at0x11c0cc and calls0x116cf0.
- That function branches on command word0/1/2, as DisplayManagement expects.
  Command0 publishes event0x1695 (activate) with no payload at0x116d98-6da4.
  Command1 publishes event0x1697 (deactivate) at0x116e18-6e24.
  Command2 reads rate word+4 and publishes event0x1699, length4, at0x116eb0-6ec0.
  The adjacent native diagnostic strings explicitly name the SCDA map requests.
- Response paths publish event0x1694 with12-byte payload at0x11708c,
  0x1171e4 and0x117318. Detailed result/rate data flow remains to be audited.

This corroborates the formerly uncertain application0x55 boundary and its
request shape. NavigationServer handles the SCDA requests, not a direct
DisplayManagement0x1693 message. No fixed active cluster geometry is proven.
